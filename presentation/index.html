01 / LOCATORS

locator.within()

למצוא את הכפתור — אבל רק בתוך הדיאלוג

כניסה לחלק הראשון.
THE PROBLEM

שני כפתורי Save באותו עמוד

אם נחפש getByRole('button', { name: 'Save' }), נקבל 2 תוצאות — והטסט ייכשל בגלל strict mode.

$ npx playwright test ✘ click Save Error: locator.click: Error: strict mode violation: getByRole('button', { name: 'Save' }) resolved to 2 elements: 1) <button class="primary" id="save-profile">Save</button> aka locator('#save-profile') 2) <button class="primary" id="save-settings">Save</button> aka getByTestId('settings-dialog').getByRole('button', { name: 'Save' })

כבר יש לנו לוקייטור לכפתור ולוקייטור לדיאלוג.

מ-1.64 אפשר לחבר ביניהם בדיוק כמו שהיינו אומרים את זה במילים: הכפתור, בתוך הדיאלוג.

הקוד: saveButton.within(dialog)

test('save the store settings', async ({ page }) => {
  await page.goto('/settings');
  await page.getByRole('button', { name: 'Open store settings' }).click();

  const saveButton = page.getByRole('button', { name: 'Save' }); // 2 matches!
  const dialog = page.getByTestId('settings-dialog');

  await expect(saveButton).toHaveCount(2);
  await expect(saveButton.within(dialog)).toHaveCount(1);

  await saveButton.within(dialog).click();
  await expect(dialog).toBeHidden();
});

עד עכשיו כתבנו dialog.getByRole(...). זה עובד, אבל צריך לבנות את הלוקייטור מחדש מתוך הדיאלוג. עם within() פשוט משתמשים בשני הלוקייטורים שכבר יש לנו.

לעבור שורה-שורה עם ההדגשות. בסוף להריץ: npx playwright test 01-within --headed.
RELATIVE LOCATORS · PER PARENT

עוד דוגמה: עמודה שלמה בטבלה

בלי within 
page.getByRole('cell').nth(2)
// → ['Apple']

כאן nth(2) רץ על כל התאים בטבלה ביחד, ולכן מקבלים תא אחד בלבד: התא השלישי בטבלה כולה.

עם within 
page.getByRole('cell').nth(2)
  .within(page.getByRole('row'))
// → ['Apple', 'Banana', 'Cherry']

עכשיו nth(2) רץ בתוך כל שורה בנפרד, ומקבלים את התא השלישי של כל שורה. עמודה שלמה, בלי לולאה.

בדמו: בלי ה-lock כל 3 הריצות נכשלו. עם ה-lock — כל 3 עברו.

ללחוץ "בלי lock" — שני הבלוקים הכתומים חופפים ונהיים אדומים. "עם lock" — אחד זז אחרי השני, והשאר ממשיכים במקביל. Test Locks הגיעו ב-1.63. ב-1.64 אפשר להגדיר lock לקובץ שלם או ל-describe שלם.
test.describe.configure({ lock })

חדש ב-1.64: lock לקובץ שלם או ל-describe שלם

// every test in this file takes the lock
test.describe.configure({ lock: 'store-settings' });

test('switch theme to dark', async ({ page }) => {
  // ...changes the shared server setting
});
test.describe.configure({ lock: 'store-settings' });

test('switch theme to light', async ({ request }) => {
  // never runs together with locks-a
});

// built-in: nothing else runs meanwhile
test('reset', { lock: 'exclusive' }, async () => {});
  • ה-lock תקף בין קבצים, workers ו-projects. אם קוראים ל-configure שוב, ה-locks מצטברים ולא מחליפים זה את זה.
  • במצב default או serial ה-lock תפוס לאורך כל הקובץ, אז כדאי שקבצים עם lock יהיו קטנים.
  • עדיף לתת לכל worker משאב משלו (למשל משתמש נפרד), ולהשתמש ב-lock רק כשאין ברירה.
ה-lock 'exclusive' הוא מובנה (מ-1.63). המלצות 2-3 מ-currents.dev ומהתיעוד הרשמי.

04 / WEBMCP

WebMCP

האתר חושף כלים לסוכני AI — ואנחנו בודקים אותם כמו כל חלק אחר באפליקציה

WHAT IS WEBMCP

האתר מגדיר כלים, הדפדפן מציג אותם, וסוכן ה-AI מפעיל אותם

המפתחים של האתר בוחרים אילו פעולות לחשוף. לכל כלי יש שם, תיאור, JSON Schema ופונקציה שמבצעת אותו.

עדיין ניסיוני: ב-Chromium מפעילים עם --enable-features=WebMCP, ב-Firefox דרך prefs, וב-WebKit אין תמיכה.

אין LLM בטסט. קוראים לכלי עם קלט קבוע ובודקים את התוצאה — כמו טסט ל-API. ב-awesome-testing קוראים לזה tool contract test.

המקורות: התיעוד הרשמי של class WebMCP, והמאמר של awesome-testing על WebMCP עם Playwright. להדגיש: תיאורים ותוצאות של כלים מגיעים מהעמוד — Playwright ממליץ להתייחס אליהם כקלט לא אמין.
demo-app/public/index.html

בצד של האתר: מגדירים כלי

const modelContext = document.modelContext || navigator.modelContext;

modelContext.registerTool({
  name: 'add_to_cart',
  description: 'Adds a product to the cart. Changes the cart contents.',
  inputSchema: {
    type: 'object',
    additionalProperties: false,
    properties: { productId: { type: 'integer', minimum: 1 }, quantity: { type: 'integer', minimum: 1 } },
    required: ['productId', 'quantity'],
  },
  async execute({ productId, quantity }) {
    const cart = await api('/api/cart', { method: 'POST', body: JSON.stringify({ productId, quantity }) });
    if (cart.error) return { isError: true, content: [{ type: 'text', text: cart.error }] };
    renderCart(cart);
    return { content: [{ type: 'text', text: JSON.stringify(cart) }] };
  },
});

BREAKING CHANGES ⚠️

4 Breaking Changes — כדאי לבדוק לפני שמשדרגים

📐 screen נלקח מהגדרות המכשיר

מי שמשתמש ב-devices['Desktop Chrome'] יקבל עכשיו גם גודל מסך של 1920×1080, וה-viewport נשאר 1280×720. כדי לוותר על זה מגדירים screen: undefined.

👻 iframe מוסתר

אלמנט שנמצא בתוך iframe מוסתר, למשל עם visibility: hidden, נחשב עכשיו לא נראה. זה משפיע על פעולות, על isVisible() ועל toBeVisible().

📸 --update-snapshots=missing

טסט שרק יוצר snapshot חסר עובר עכשיו בהצלחה. המצב הרגיל נקרא מעכשיו 'default'.

⚛️ JSX בטסטים

JSX בקבצי הטסט מתקמפל עכשיו לפי tsconfig.json, כולל ההגדרות jsx ו-jsxImportSource. ברירת המחדל היא automatic runtime של react/jsx-runtime.

את שני הראשונים מדגימים ב-04-breaking-changes.spec.ts. בדמו: הכפתור ב-iframe נמצא ב-DOM (count 1) אבל toBeHidden עובר. טיפ מ-currents: אפשר להגדיר זמנית screen: undefined, כדי להבדיל בין שינוי ויזואלי בגלל גודל המסך לבין באג אמיתי.
tests/04-breaking-changes.spec.ts

איך זה נראה בטסט

// project uses ...devices['Desktop Chrome']
await page.goto('/widgets');
await expect(page.locator('#screen-size'))
  .toHaveText('1920×1080');

// opt out
const context = await browser.newContext({
  ...devices['Desktop Chrome'],
  screen: undefined,
});
// → screen follows the viewport: 1280×720
const chatButton = page
  .frameLocator('#hidden-frame')
  .getByRole('button', { name: 'Chat with us' });

await expect(chatButton).toHaveCount(1); // in the DOM
await expect(chatButton).toBeHidden();   // 1.64: hidden
expect(await chatButton.isVisible()).toBe(false);
ערכי המסך פה הם מה שראינו בפועל בהרצה של הדמו.
