INSTALL · UPGRADE

מתקינים או משדרגים ל-1.64

$ npm install -D @playwright/test@latest $ npx playwright --version Version 1.64.1

ב-CI: גם ספריות מערכת

$ npx playwright install --with-deps

מתקין גם את ספריות מערכת ההפעלה שהדפדפנים צריכים. לפי התיעוד, זה שימושי בעיקר בסביבות CI.

למה צריך להוריד דפדפנים אחרי כל שדרוג?

כל גרסה של Playwright צריכה גרסאות מסוימות של הדפדפנים. ב-1.64 אלה Chromium 156, Firefox 157 ו-WebKit 27.2, וצריך להתקין אותן עם ה-CLI של Playwright.

הדפדפנים נשמרים בתיקייה משותפת לכל הפרויקטים, למשל ~/Library/Caches/ms-playwright ב-macOS. גרסה שאף פרויקט כבר לא צריך נמחקת אוטומטית.

שלב 1: npm install -D @playwright/test@latest — זה מה שהתיעוד ממליץ (Updating Playwright), ואחריו playwright install --with-deps. שלב 2: דפדפנים. שלב 3: with-deps ל-CI. שלב 4: למה — "Each version of Playwright needs specific versions of browser binaries". בשקופית הבאה: מה קורה אם שוכחים.

THE PROBLEM

שני כפתורי Save באותו עמוד

LOCATOR.WITHIN() · BEFORE / AFTER

הקוד: לפני ואחרי within()

ב-1.64 
test('save settings', { lock: 'store-settings' }, async ({ page }) => {
  await page.goto('/settings');
  await page.getByRole('button', { name: 'Open store settings' }).click();

  const saveButton = page.getByRole('button', { name: 'Save' }); // 2 matches!
  const dialog = page.getByTestId('settings-dialog');

  await expect(saveButton).toHaveCount(2);
  await expect(saveButton.within(dialog)).toHaveCount(1);

  await dialog.getByLabel('Theme').selectOption('light');
  await saveButton.within(dialog).click();

  await expect(dialog).toBeHidden();
  await expect(page.locator('#theme')).toHaveText('light');
});
עד 1.64 
test('save settings', { lock: 'store-settings' }, async ({ page }) => {
  await page.goto('/settings');
  await page.getByRole('button', { name: 'Open store settings' }).click();

  const dialog = page.getByTestId('settings-dialog');
  await dialog.getByLabel('Theme').selectOption('light');
  await dialog.getByRole('button', { name: 'Save' }).click();

  await expect(dialog).toBeHidden();
  await expect(page.locator('#theme')).toHaveText('light');
});

מתחילים מההורה ובונים את הלוקייטור מחדש בתוכו: dialog.getByRole(...). עובד גם היום, אבל עם within() משתמשים בשני הלוקייטורים שכבר יש לנו.

לעבור שורה-שורה עם ההדגשות בצד של 1.64. בסוף (חץ) מופיע הקוד של עד 1.64 — אותו טסט, מתחיל מהדיאלוג. שני הקבצים רצים: npx playwright test within.
RELATIVE LOCATORS · PER PARENT

עוד דוגמה: עמודה שלמה בטבלה

בלי within ← רק Apple 
const thirdCell = page.getByRole('cell').nth(2);
await expect(thirdCell).toHaveText('Apple');

nth(2) נספר על כל התאים בטבלה, ולכן מקבלים תא אחד.

ב-1.64: עם within ← כל העמודה 
const thirdColumn = page.getByRole('cell').nth(2)
  .within(page.getByRole('row'));
await expect(thirdColumn).toHaveText(['Apple', 'Banana', 'Cherry']);

nth(2) נספר בתוך כל שורה בנפרד: תא אחד מכל שורה.

const rows = page.getByRole('row').filter({ has: page.getByRole('cell') });
const names: string[] = [];
for (const row of await rows.all())
  names.push(await row.getByRole('cell').nth(2).innerText());

SHUFFLE · IN PRACTICE

shuffle בפרויקט אמיתי: 3 דברים שכדאי לדעת

🌙

מריצים בריצת הלילה, לא בכל PR

הכישלון ש-shuffle מוצא הוא אקראי. אם הוא ירוץ על כל PR, מפתח שבכלל לא נגע בטסטים האלה ייחסם. לכן נריץ אותו בלילה, ונשמור את ה-seed מהלוג כדי לשחזר את הכישלון.

$ npx playwright test --shuffle Running 19 tests using 5 workers, shuffle seed 427311825
🧩

בלי fullyParallel מתערבבים רק הקבצים

shuffle תמיד משנה את סדר הקבצים. כדי שגם הטסטים בתוך אותו קובץ יתערבבו, הקובץ צריך לרוץ במצב parallel.

fullyParallel: true,
🔗

איפה shuffle לא יעזור: beforeAll משותף

טסטים שחולקים beforeAll רצים כקבוצה, לפי הסדר שבו נכתבו. shuffle מערבב את הקבוצות, אבל לא את הטסטים שבתוכן. לכן תלות בין שני טסטים כאלה shuffle לא יתפוס.

בלי beforeAll, shuffle מערבב את הטסטים, ולכן חלק מהריצות נכשלות. עם beforeAll משותף הם רצים תמיד באותו סדר, ולכן הם עוברים, והבאג נשאר מוסתר.

שני הקבצים נמצאים ב-tests/shuffle/with-1-64, עם אותם טסטים בדיוק. ההבדל היחיד הוא ה-beforeAll.

כרטיס 1: למה לא על כל PR — כישלון אקראי חוסם אנשים שלא קשורים. כרטיס 2: בלי fullyParallel רק סדר הקבצים משתנה. כרטיס 3: המסר הוא לא "תורידו beforeAll", אלא "דעו איפה shuffle עיוור". בקוד של Playwright (createTestGroups) טסטים במצב parallel עם beforeAll/afterAll משותף נארזים בקבוצות לפי סדר הכתיבה, ו-shuffle מערבב רק קבוצות. בקובץ cart-order-beforeall.spec.ts זה הסתיר את התלות; כשהורדנו את ה-beforeAll, הטסט התלוי נכשל בחלק מהריצות.
TEST LOCKS

למה צריך lock?

שני טסטים משנים את אותה הגדרה בשרת (theme), ו-Playwright עלול להריץ אותם באותו זמן.

בלי lock — רצים באותו זמן
  1. Aשומר theme = darkבשרת: dark
  2. Bשומר theme = lightבשרת: light
  3. Aבודק: מצפה ל-dark, אבל מקבל light✘
  4. Bבודק: מצפה ל-light ומקבל light✓

A נכשל, למרות שאין באג באפליקציה. B פשוט דרס לו את ההגדרה באמצע.

עם lock: 'store-settings' — אחד אחרי השני
  1. A🔑 תופס את ה-lock
  2. B⏳ מבקש את אותו lock, הוא תפוס, אז מחכה
  3. Aשומר dark ובודק✓
  4. Aמסיים ומשחרר את ה-lock
  5. B🔑 תופס, שומר light ובודק✓

שניהם עוברים. כל שאר הטסטים, שאין להם את ה-lock הזה, ממשיכים לרוץ במקביל כרגיל.

בלי lock אחד הטסטים נכשל, כי השני דורס לו את ההגדרה באמצע. עם lock הם רצים אחד אחרי השני, ושניהם עוברים.

שלב 1: בלי lock — לעבור על 4 השורות לפי הסדר: A נכשל בלי באג. שלב 2: עם lock — B מחכה, A מסיים ומשחרר, B רץ. אנלוגיה: מפתח יחיד לחדר ישיבות. Test Locks הגיעו ב-1.63.
test.describe.configure({ lock })

הדוגמה: אותם שני טסטים, עם lock ובלי

test.describe.configure({ lock: 'store-settings' });

test('switch theme to dark', async ({ request }) => {
  await request.put('/api/settings', { data: { theme: 'dark' } });
  const settings = await (await request.get('/api/settings')).json();
  expect(settings).toEqual({ theme: 'dark' });
});

test('switch theme to light', async ({ request }) => {
  await request.put('/api/settings', { data: { theme: 'light' } });
  const settings = await (await request.get('/api/settings')).json();
  expect(settings).toEqual({ theme: 'light' });

עם lock

שני הטסטים מתחילים באותו רגע, ולכן בלי lock הם מתנגשים גם בלי שום המתנה בקוד. מדדנו: בלי lock אחד נכשל בכל ריצה (5/5), עם lock שניהם עוברים בכל ריצה (5/5). הפלט בשקופית אמיתי (קיצרנו רק את הנתיב של כל טסט).
SNAPSHOTS

צילומי מסך בפורמט WebP

NEW · type: 'webp'

מה זה WebP? פורמט תמונה, כמו PNG. ב-Playwright צילומי ההשוואה נשמרים בו בלי איבוד מידע (lossless), כך שההשוואה מדויקת בדיוק כמו עם PNG.

עד 1.64 צילום בלי שם נשמר תמיד כ-.png. WebP היה אפשרי רק עם שם שמסתיים ב-.webp (מגרסה 1.62).

ב-1.64 שורה אחת בקונפיג, וכל הצילומים בלי שם נשמרים כ-WebP:

expect: {
  // NEW in 1.64: store unnamed toHaveScreenshot() baselines as WebP
  toHaveScreenshot: { type: 'webp' },
},

מדדנו בדמו את אותם צילומי מסך בשני הפורמטים, ו-WebP יצא גדול יותר: דף החנות 81 KB מול 48 KB ב-PNG. לכן נמדוד על הפרויקט שלנו לפני שמחליפים.

להראות את קובץ ה-webp ב-tests/snapshots/with-1-64/webp.spec.ts-snapshots. WebP עם שם קיים מ-1.62. המדידה (צילום עמוד מלא, Chromium, macOS): shop 48KB PNG / 81KB WebP, settings 25/61, widgets 48/107. התיעוד: "Both formats are lossless". חיסכון בגודל מוזכר רק ל-page.screenshot עם quality נמוך (lossy).
SNAPSHOTS · BREAKING

מה קורה כשעוד אין צילום להשוואה?

toHaveScreenshot() משווה את המסך לצילום שמור. בריצה הראשונה של טסט חדש אין עדיין צילום כזה, ולכן אין מול מה להשוות. Playwright שומר את הצילום הנוכחי כצילום הבסיס, ומכשיל את הטסט כדי שמישהו יסתכל על התמונה לפני שהיא נחשבת לנכונה.

בלי הדגל

הריצה הרגילה, בלי --update-snapshots. ההתנהגות שלה לא השתנתה. ב-1.64 היא רק קיבלה שם, default, כך שאפשר לכתוב גם --update-snapshots=default וזה אותו דבר.

הצילום נשמר, והטסט נכשל. בריצה הבאה יש מול מה להשוות, והטסט עובר.

עם הדגל

בשביל מה הדגל? כתבנו טסט חדש ורוצים ליצור לו את הצילום הראשון. missing יוצר רק צילומים שעוד לא קיימים, ולא נוגע בצילומים שכבר שמורים:

שני הפלטים אמיתיים מהריצה על הדמו (קיצרנו רק את הנתיב). 04 / WEBMCP

WebMCP

האתר חושף כלים לסוכני AI — ואנחנו בודקים אותם כמו כל חלק אחר באפליקציה

WHAT IS WEBMCP

WebMCP: האתר נותן לסוכן AI פעולות מוכנות

MCP (Model Context Protocol) הוא הדרך שבה סוכן AI מקבל "כלים", כלומר פונקציות שהוא יכול להפעיל. WebMCP הוא אותו רעיון, אבל הכלים מגיעים מתוך דף אינטרנט. נניח שסוכן AI צריך להוסיף 2 בננות לעגלה בחנות הדמו שלנו:

בלי WebMCP

הסוכן משתמש באתר כמו אדם: מסתכל על הדף, מחפש את הכפתור הנכון ולוחץ.

  1. קורא את הדף ומחפש את המוצר
  2. מוצא את הכפתור Add to cart ולוחץ
  3. מנחש מהמסך אם זה הצליח

כל שינוי בעיצוב הדף יכול לבלבל אותו.

עם WebMCP

האתר עצמו מכריז: "יש לי פעולה בשם add_to_cart, והיא מקבלת מוצר וכמות". הסוכן קורא לה ישירות, כמו לפונקציה:

add_to_cart({ productId: 2, quantity: 2 }) → { totalItems: 2, totalPrice: 15 }

תשובה מסודרת, בלי לנחש מהמסך.

ומה הקשר ל-Playwright? אם האתר שלנו חושף כלים כאלה, צריך לבדוק שהם עובדים. ב-1.64 יש page.webmcp: מקבלים את רשימת הכלים של הדף וקוראים לכלי עם קלט קבוע, בלי מודל AI בטסט, כמו טסט ל-API. התכונה עדיין ניסיונית: ב-Chromium צריך את הדגל --enable-features=WebMCP.
הדוגמה אמיתית: הכלי add_to_cart מוגדר ב-demo-app/public/index.html, והתוצאה { totalItems: 2, totalPrice: 15 } היא מה שהטסט ב-tests/webmcp/with-1-64/webmcp.spec.ts בודק. המקורות: התיעוד הרשמי של class WebMCP, והמאמר של awesome-testing על WebMCP עם Playwright. ב-Playwright MCP הכלים של הדף מוצעים לסוכן כ-webmcp_<tool>. Firefox דרך prefs, WebKit בלי תמיכה. תיאורים ותוצאות של כלים מגיעים מהעמוד, ולכן Playwright ממליץ להתייחס אליהם כקלט לא אמין.

BREAKING CHANGES ⚠️

4 שינויים שיכולים לשבור טסטים קיימים

📐 גודל המסך מגיע מהמכשיר (screen)

מה השתנהיש שני גדלים: viewport הוא החלון שבו הדף מוצג, ו-screen הוא גודל המסך כולו (window.screen). עם devices['Desktop Chrome'] ה-screen הוא עכשיו 1920×1080, ולא כמו ה-viewport (1280×720).
איך נשים לבדף שמתאים את עצמו לגודל המסך יכול להיראות אחרת, וצילומי השוואה להשתנות.
מה עושיםבודקים את הצילומים. כדי לחזור להתנהגות הקודמת: screen: undefined.

👻 אלמנט בתוך iframe מוסתר נחשב מוסתר

מה השתנהאם ה-iframe עצמו מוסתר (למשל visibility: hidden), גם כל מה שבתוכו נחשב עכשיו לא נראה. קודם Playwright בדק רק את האלמנט ולא את ה-iframe שמסביבו.
איך נשים לבtoBeVisible() שעבר מתחיל להיכשל, ו-click() על אלמנט כזה מחכה עד timeout.
מה עושיםבדרך כלל זה נכון: משתמש לא יכול לראות את הכפתור. אם הטסט צריך אותו, קודם מציגים את ה-iframe.

📸 --update-snapshots=missing עובר

מה השתנהטסט שרק יצר צילום חסר עובר עכשיו, במקום להיכשל. ריצה רגילה, בלי הדגל, עדיין נכשלת.
איך נשים לבסקריפט CI שרץ עם missing יוצא ירוק גם כשנוצרו צילומים חדשים.
מה עושיםב-CI מריצים בלי הדגל (ראינו בשקופית של צילומי המסך).

⚛️ JSX בטסטים לפי tsconfig.json

מה השתנהJSX הוא התחביר של React (<Button />). Playwright מקמפל אותו עכשיו לפי jsx ו-jsxImportSource שב-tsconfig.json. בלי הגדרה: react/jsx-runtime.
איך נשים לברלוונטי רק למי שכותב JSX בקבצי הטסט, למשל ב-component testing. מי שלא, לא מושפע.
מה עושיםבודקים שההגדרות ב-tsconfig.json מתאימות לספרייה שלנו.
את שני הראשונים מדגימים בשקופית הבאה (tests/breaking-changes/with-1-64/breaking-changes.spec.ts). בדמו: window.screen הוא 1920×1080 וה-viewport 1280×720; הכפתור ב-iframe נמצא ב-DOM (count 1) אבל toBeHidden עובר. טיפ מ-currents: אפשר להגדיר זמנית screen: undefined, כדי להבדיל בין שינוי ויזואלי בגלל גודל המסך לבין באג אמיתי. ה-JSX: לפי ה-release notes של 1.64; אין לזה דמו בריפו.

ב-1.64 המסך גדול מהחלון, כמו במחשב אמיתי.

דף הדמו /widgets מציג על המסך את שני הגדלים, והטסט בודק את מה שהוא מציג:

await page.goto('/widgets');
await expect(page.locator('#screen-size')).toHaveText('1920×1080');
await expect(page.locator('#viewport-size')).toHaveText('1280×720');

בדף הדמו יש iframe מוסתר, ובתוכו כפתור צ'אט. משתמש לא רואה אותו, ועכשיו גם Playwright מסכים:

const chatButton = page
  .frameLocator('#hidden-frame')
  .getByRole('button', { name: 'Chat with us' });

await expect(chatButton).toHaveCount(1); // in the DOM…
await expect(chatButton).toBeHidden();   // …but hidden
expect(await chatButton.isVisible()).toBe(false);
לחיצה 1: המסך גדל ל-1920×1080 (ההתנהגות של 1.64). לחיצה 2: הכפתור ב-iframe עובר ל"לא נראה". הערכים אמיתיים: הטסט עובר ב-1.64 עם 1920×1080 ו-1280×720, ועם screen: undefined מקבלים 1280×720 (הטסט השני בקובץ).

איך משדרגים בלי הפתעות

נשדרג קודם בלי shuffle — כדי שכישלונות בגלל ה-Breaking Changes לא יתערבבו עם כישלונות בגלל סדר הטסטים.

נריץ פעם אחת בדיוק כמו ב-CI ונשווה לריצה הקודמת: אותו מספר טסטים? אותם פרויקטים?

כשהכול ירוק — נוסיף ריצת לילה עם --shuffle. כל לילה ירוץ בסדר אקראי אחר, וזו בדיוק המטרה. ה-seed נדפס בלוג של הריצה: אם משהו נכשל, נריץ --shuffle <seed> ונקבל בדיוק את אותו סדר כדי לשחזר את הכישלון.

נוסיף locks רק במקומות שבהם טסטים חולקים משאב שאי אפשר לשכפל.
